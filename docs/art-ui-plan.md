## 已确认方向与暂定选择

| 内容 | 当前结论 | 性质 |
| --- | --- | --- |
| 开发顺序 | 先做美术/UI 视觉验证，再完善玩法规则 | 用户目标 |
| 角色用途 | 替代玩家颜色所代表的身份；当前不设计专属技能 | 用户已确认 |
| 首个样板 | 选角色 → 个人栏显示身份 → 统一派遣面板选岗位 → 确认派遣 → 占用、场景船员与资源同步 → 下一位玩家 | 用户已确认交互方向；UI-03/04 分步接通 |
| 首个角色 | 优先用拉坎，已有卡面与船员素材 | 暂定，可随视觉反馈调整 |
| 预览人数 | 以原版五人满员状态检查布局；六张可选角色不等于六人局 | 样板约定 |
| 预览平台 | 先沿用当前桌面横屏工程；移动端布局尚未确定 | 暂定 |
| 预览数据 | 使用可重置的固定数据，不依赖完整规则引擎 | 制作约定 |
| 整体画风 | 以现有像素海港和角色卡 UI 为起点；最终风格尚未定稿 | 待样板验证 |

以下问题在制作对应样板时用实际画面比较，并记录结论，不必在每个新对话里重新询问：

- 角色卡偏历史冒险，海港有现代设施：最终采用哪种年代感，或明确采用架空混搭。
- 角色、背景、船员、立体骰子的像素颗粒、描边、细节密度是否协调。
- 横向长地图如何提供全局信息；镜头移动时如何持续看见三船进度和关键操作。
- 玩家身份用头像、徽记和辅助色共同识别；货物颜色承担独立含义。

## 影响美术与布局的原版规则

参考：[原版规则全文转载（UltraBoardGames）](https://www.ultraboardgames.com/manila/game-rules.php)。以下仅保留影响视觉制作的结构；完整顺序、数值和特殊情况见[原版规则参考](manila-rules.md)。

- 每轮航程包括竞拍港务长、购买股票机会、选择货物与起点、派人和三次航行、收益结算、货价上涨。
- 有玉石、人参、丝绸、肉豆蔻四种货物，每轮选择三种，分别装入三艘船。货物、骰子、股票、行情图标需要对应。
- 原版支持 3–5 人；4–5 人时每人三个小人，3 人时每人四个。个人栏要能展示这两种数量。
- 一艘船可以有不同玩家的小人，同一玩家也能在同船放多个小人。**角色代表玩家，三艘船是共同参与的对象，不是角色专属船。**
- 玉石有四个船位，其余货物各三个。座位外观要容纳两种容量。
- 岗位包括船位、港口、修船厂、海盗、引航员、保险；需要统一呈现空位、占用、费用和效果。
- 航线为 0–13，通常越过 13 到港；13 号位另有海盗及结算特例，不能简单画成普通终点。起点为 0–5，三船起点之和为 9。
- 自己的持股与公共行情分开显示；初始股票是隐藏信息，不能为了总览默认公开对手持仓。
- 最终财富由现金、股票价值及未偿贷款共同构成；某种货物行情达到 30 触发结束。终局画面要能解释财富来源。

### UI-02：当前操作者底栏与紧凑阶段提示

- **状态**：已完成（2026-09-16 用户明确确认“我看过了没问题，这一步可以结束，开始下一步了”）。
- **依赖**：UI-01（已获用户确认），沿用个人栏头像和身份表现。
- **范围**：取消顶部五人常驻卡片；底栏随当前操作者同步头像、现金、剩余小人和个人持股。航程仅在底栏显示一次，其上方的小阶段牌分别显示派遣轮或航行次数；右侧四货价格为公共行情，不随换人改变。
- **港务长**：当前操作者担任时，在头像左侧环绕“港务长”三个字；其他人担任时，显示其姓名和“下家／后 N 位”，不改变当前行动人。

### UI-03：统一派遣面板与场景船员展示

- **状态**：已完成（2026-09-24 用户明确确认"ui-03 可以验收了"）。
- **依赖**：UI-01、UI-02 已验收；复用已有座位选择逻辑、玩家身份与船体遮挡基础。
- **范围**：在同一个可展开/收起的面板内画出三艘船、港口、修船厂、海盗、小/大引航员和保险公司；所有岗位的放置选择入口本步一起呈现，不再推迟到 UI-06 才出现。
- **位置表现**：各类岗位显示费用、空位、悬停、选择、占用归属与简短作用；三艘船按货物显示三座或四座。费率与容量以 `manila-rules.md` R02 为准。
- **场景职责**：场景三船仅显示已经确认上船的人，不保留可点击座位、费用按钮或未确认小人预览；所有船默认不放固定人物。面板与场景共享同一份占用数据，不分别维护放人结果。

### UI-04：确认面板与一次派人流程

- **状态**：已完成（2026-10-08 用户明确确认“测试已过，把测试相关的ui都去掉把，然后告诉我下一步要做什么了”）。
- **依赖**：UI-01、UI-02、UI-03。
- **范围**：在统一派遣面板选中任意岗位后，显示当前角色、目标、费用/即时效果、“确认派遣”“取消”；确认后写入统一占用数据，更新金币与剩余伙计，并切换下一位演示玩家的整套底栏。若目标是船位，场景对应船同步出现人物；其他岗位只更新面板占用。
- **数据**：固定预览数据使用规则 R02 的各岗位费率；保险免费派驻并立即领取 10，仅执行一次。保险赔付、海盗事件、引航位移与收益结算仍由后续任务接入。
- **状态**：取消或收起不改变数据，也不等于放弃本航程；费用不足、没有伙计、位置被占或船已到港时明确提示不可确认；确认时重新检查，一次确认只执行一次。借款与贫困登船的完整入口仍留给 UI-11。
- **预览**：专用 `tools/boat_seat_check.gd` 保留重置与固定占位数据，反复播放“打开统一面板 → 选岗位 → 确认 → 更新占用及场景显示 → 数字更新 → 下一位玩家”；这些工具仅由检查脚本创建，正常 F5 不显示临时工具条、试掷、重置或造占位入口。
- **验收**：船位及各类特殊岗位均走通成功/取消路径；重复点击不重复扣款、领保险金或生成人物；场景船始终不可直接放人，只有确认上船才出现对应伙计。
- **交付**：可重复的完整演示、关键状态截图或短录屏、验证结果。

## 每次子任务的交付与验证

1. 开始时只读快速接手、相关约定、当前任务、必要文件和最新交接记录；确认现有工程状态。
2. 每次围绕一个界面或一段交互；先明确当前要调整什么，依赖缺失时处理最小依赖。调整期间不为每轮工作修改进度文档。
3. 使用实际场景或独立预览入口展示效果；演示数据应方便重置、更换。
4. 对新增/修改的界面看真实渲染截图，确认文字、层级、遮挡、交互状态及桌面窗口缩放。只运行与本次变更相关的检查。
5. 有行为变化时验证对应路径，例如确认、取消、重复点击；纯美术调整以视觉核验为主，不添加只重复实现的测试。
6. 做出效果后交给用户查看，继续按反馈调整。只有用户明确表示满意后，才统一更新任务状态、交接记录和顶部的后续任务；实现与占位范围要写清楚。
7. “已完成”必须同时满足必要实现与检查完成、用户认可该项 UI 效果。截图、测试通过或助手认为效果不错，都不能代替用户验收；未获认可不自动推进下一项。

状态统一使用：**待做 / 进行中 / 待确认 / 需调整 / 已完成**。视觉决定在用户确认后写入决策表；仍在尝试的选择不记为定稿。UI-01、UI-02、UI-03、UI-04 已获确认；下一项 UI-05 待做，未获开始实施授权。
